# ADR-001: Hexagonal architecture with ports and adapters

| Field | Value |
|---|---|
| Status | Proposed |
| Date | 2026-11-27 |
| Release | v0.1 |

## Context

JudgeLab calls foundation models from several providers (OpenAI-compatible APIs, Anthropic, and later others), for two roles: the target and the judge. The evaluation rules are the valuable part: what counts as PASS, FAIL or ERROR, when to stop a run, and how to score it. They must not change when a provider changes, and they must be testable without network, keys or cost (REQ-003, REQ-012).

The forces:

- Providers differ in SDKs, request shapes (where the system prompt goes), response shapes and error types.
- Tests need a deterministic model that can be scripted to answer, refuse or fail.
- The project is small (v0.1 is one CLI), so every abstraction must pay for itself now.

## Decision

Organise the code as a hexagon (ports and adapters):

- **Core:** benchmark, judge, scoring and report building. It knows nothing about SDKs, HTTP, files or YAML.
- **Driven port:** `ModelConnector`, whose `generate(prompt, *, instructions=None)` returns a `ModelResponse` or raises a `ConnectorError` subclass. The port's types (`ModelResponse`, the `ConnectorError` family) are JudgeLab's own, so no SDK type crosses into the core.
- **Adapters:** `OpenAIConnector` and `AnthropicConnector` wrap the official SDKs. Each translates the SDK's response and exceptions (an anti-corruption layer). `FakeConnector` is a scripted adapter for tests.
- **Driving adapter:** the `judgelab` CLI, with the YAML configuration loader. It is also the **composition root**: it builds the connectors from connection profiles through an injected `connector_factory` (default `create_connector`) and passes them in.
- **Ports only where they pay now.** File and environment access stay plain functions at the edge in v0.1: `load_benchmark`, `write_report`, `utc_now` and `read_secret`. A port is added when a second adapter appears, or when a test needs to substitute the dependency.

See the architecture diagram in [design.md](../design.md).

## Alternatives considered

| Option | Pros | Cons |
|---|---|---|
| Call the SDKs directly from the runner and judge | Least code | Provider details leak everywhere; switching the judge means code changes; tests need HTTP mocking or keys |
| Use a multi-provider library (e.g. LiteLLM) behind no port | One dependency covers many providers | Ties the core to that library's types and error model; less to learn about how providers really differ |
| Full hexagon: ports for every I/O (dataset, report, clock, secrets) | Uniform; everything substitutable | Four interfaces with one implementation each; ceremony without a current need (YAGNI) |
| **Hexagon with one driven port now, others when needed** (chosen) | Isolates the part that varies (providers); keeps tests free; small | Edge I/O is not yet swappable; the port lives in `judgelab.connectors` beside its adapters rather than in a core package |

## Consequences

- Switching the target or the judge is a configuration change (AC-001-22, AC-004-05).
- Every behaviour can be tested with `FakeConnector`; contract tests run the same checks against every adapter (AC-001-09).
- Adding a provider means one new adapter class and one registry entry; the core is untouched (Open/Closed).
- Patterns: Adapter, Strategy (interchangeable connectors), Factory/Registry (`create_connector`), Dependency Injection (`connector_factory`, `Judge(connector, rubric)`), Test Double (`FakeConnector`).
- Candidate ports for v0.2: `BenchmarkSource` (e.g. Moonshot datasets), `ReportSink`, `Clock`. Moving `ModelConnector` into a core package would make the dependency rule visible in the folder layout.
