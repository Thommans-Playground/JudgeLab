# ADR-002: PlantUML diagrams with an as-built check

| Field | Value |
|---|---|
| Status | Proposed |
| Date | 2026-11-27 |
| Release | v0.1 |

## Context

Each use case is realised through OOAD: analysis (what, in problem terms) and then design (how, in code terms), both drawn as class and sequence diagrams. Diagrams drift from code unless something checks them. We want diagrams that:

- are text, so they diff and review like code;
- support real UML: stereotypes, boundary/control/entity, abstract classes, interaction frames;
- can be compared with what the code actually does.

## Decision

1. **PlantUML source** (`.puml`) lives next to what it describes:
   - use-case diagrams in `docs/usecases/UC-###-<slug>/diagrams/`;
   - architecture diagrams in `docs/diagrams/`;
   - all of them include the shared `docs/diagrams/style.iuml`.
2. **Per use case:** `analysis.md` (system sequence diagram, BCE analysis classes, analysis sequence) and `design.md` (design classes, design sequences for the main flow and key extensions, traceability from analysis classes to code).
3. **Diagrams are read through a PlantUML preview** (e.g. the VS Code PlantUML extension); pages link to the `.puml` source. Rendered SVGs are not committed, so there is nothing to keep in sync. `render_diagrams.py` can export SVGs on demand, e.g. for slides.
4. **The as-built check.** Design diagrams are *prescriptive*: drawn before coding a slice, they show intent, abstractions and every extension. As-built diagrams are *descriptive*: generated by `asbuilt.py` from a traced test run (sequence) or by introspecting modules (classes), they show only what the code did on one path. They never replace the design. Instead, when a slice is done, generate the as-built sequence for its main scenario and compare it with the design. A difference is either:
   - **design drift:** update the design and say why, or
   - **a code defect:** fix the code.

   The generated file goes in `diagrams/as-built/` and is referenced from the task's Verification section.

## Alternatives considered

| Option | Pros | Cons |
|---|---|---|
| Mermaid | Renders natively on GitHub; already used for small ontology and domain diagrams | Weak UML: no boundary/control/entity, limited class-diagram notation, no `alt`/`opt` styling control |
| Draw.io / image files | Free-form | Binary or noisy diffs; drift is invisible |
| Generate all diagrams from code | Never out of date | Shows only what exists, not intent; no analysis level; can't design before coding |
| **PlantUML for UML + as-built generation for verification** (chosen) | Full UML, text diffs, intent and reality both visible | Needs a PlantUML preview to read; GitHub shows the source, not the picture |

## Consequences

- Reading a diagram needs a PlantUML preview (the VS Code extension renders `.puml` files in place). On GitHub the `.puml` source is shown as text.
- Small concept-level diagrams in `docs/ontology/` and `docs/domain/` stay in Mermaid, which GitHub renders without a build step. UML views of use cases and the architecture use PlantUML.
- The V-model gets a check at the design level: design diagrams on the left, the as-built comparison on the right.
